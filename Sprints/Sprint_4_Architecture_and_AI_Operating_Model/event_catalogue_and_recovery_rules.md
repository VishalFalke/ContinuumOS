# Event catalogue and idempotency/recovery rules

## Purpose and status

This is the Sprint 4 requirements-level event contract for the diagnostic-order to next-step-confirmed MVP. It is synthetic design evidence only: no event broker, production delivery guarantee or live integration is claimed.

The catalogue is derived from `architecture_principles_and_boundary.md`, the canonical Sprint 1 transition table, the Sprint 3 FHIR/field maps and `smart_on_fhir_launch_sequence.md`. It is carried into the AI service cards and audit design and remains the reference for later UAT cases and prototype failure states.

## Event design rules

- Every event carries an immutable `event_id`, `event_type`, `correlation_id`, `episode_id` (once linkage is verified), source system, source resource/event id and version, occurred/received timestamps, actor/role, idempotency key, prior/current canonical state, outcome and linked evidence.
- Source events, internal orchestration events, human decisions, deterministic controls and AI-assistive records remain distinct. An AI record never becomes a clinical, referral, financial or closure decision.
- Store minimum necessary identifiers and references, not raw SMART launch values, tokens, secrets or full source payloads. Source systems remain authoritative for source records; ContinuumOS owns orchestration visibility, tasks, exceptions and workflow history.
- Processing is **semantically once per episode and state transition**, not a claim of exactly-once transport. Duplicates are retained as evidence and do not advance the workflow twice.
- Events with uncertain patient, encounter or order linkage are quarantined in the exception queue. No silent attachment or inferred state transition is allowed.
- Recovery returns to the last verified valid state, records the reason and actor, and requires re-verification before replay. Amended/corrected reports preserve historical acknowledgement and require renewed review.

## Catalogue (22 explicit event families)

The catalogue deliberately has more than approximately ten events. The architecture view may show the major families; this detailed contract keeps materially different human authorities, evidence and corrections separate.

## Idempotency contract

1. Prefer a stable source key: `source_system | event_type | source_event_or_resource_id | source_version`. For internal events use the stable decision, assignment, package, response, confirmation, recovery or closure id plus its subject/version. Never use receive time alone.
2. Keep `correlation_id` for tracing across launch, retrieval and recovery; it is not the primary identity of a launch retry. Never retain raw launch or token values as evidence.
3. Before applying an event, check the key, expected prior state, source/current report version, required human authority and allowed canonical transition. If already applied, append duplicate evidence and return the existing outcome.
4. Keep processing outcome as `received`, `processed`, `rejected`, `quarantined` or `superseded`. A rejected or quarantined event is not silently retried as a new event.
5. Replays may rebuild evidence and metrics, but must not create a second task, acknowledgement, direction, referral send, receiving response, communication send, confirmation or closure.
6. A correction or superseding version gets a new event/idempotency key and links to the prior event; it never overwrites the historical audit entry.

## Recovery matrix

| Condition | Safe response | Human control/evidence |
|---|---|---|
| Launch/authentication failure | Stop protected retrieval; record requested/granted outcome where available; start a new authorised session only after resolution | Authorised operator verifies access; no raw credential retained |
| Source retrieval unavailable or denied | Keep last verified state; record failed retrieval attempt; retry only after availability/access verification | Operations/source owner records retry and result |
| Duplicate or out-of-order event | Retain duplicate evidence; do not advance; request source ordering/reconciliation if needed | Workflow/audit shows key, prior state and disposition |
| Uncertain linkage | Quarantine; do not attach to episode | Authorised resolver records match decision and evidence |
| Complete report without review assignment | Hold at `Result Available`; create visible unassigned/overdue control if required | Care Coordinator assigns the accountable reviewer and SLA |
| Incomplete result | Keep pending/`Result Incomplete`; request complete current report | Clinician reviews only when the approved fixture rule is met |
| Amended/corrected report | Apply E05/E06; reopen review, flag dependent decisions and reassess affected referral/communication evidence | Clinician owns renewed acknowledgement; downstream changes remain human-controlled |
| AI timeout/outage/low confidence | Mark AI assist unavailable; continue deterministic and human path | Reviewer may proceed without AI; failure is auditable |
| Communication delivered but required confirmation not recorded | Preserve delivery evidence and leave required confirmation pending; where confirmation is not required by pathway policy, record that applicability explicitly | Patient/caregiver or authorised confirming actor supplies any required confirmation |
| Recovery replay after prior recovery | Return existing recovery outcome; do not advance again | Product/platform administrator records any new recovery as a new linked action |

## Traceability and evidence status

- Canonical states and transition names are inherited from `01_Day_1_Product_Framing/state_transition_table.csv`; this catalogue adds no new workflow state. In particular, EVT-07 supports T04 only, EVT-09 supports T05 and EVT-10 supports T06.
- T04 uses the approved synthetic-fixture rule: accepted current report status (`final`, `amended` or `corrected`), current source version, resolution of configured required result references and separate source-specific completion evidence. It is not a universal FHIR DiagnosticReport rule.
- E05/E06 govern amended/corrected re-review; D13 governs AI fallback; D16 governs linked audit correction; D17 separates communication from confirmation; D18 governs linkage.
- UAT must cover duplicate final-report events, complete report without assignment, repeated/stale acknowledgement, amended report after referral approval, duplicate receiving response, delivered-but-unconfirmed communication, recovery replay, out-of-order operational events and AI timeout with human continuation.
- Evidence status: **proposed requirements and synthetic design evidence**, ready to carry into AI control cards, UAT and prototype work. It is not evidence of implemented event processing or production recovery.
